# Known Issues

코드 분석과 실행 중 발견한 이슈를 기록합니다. 해결한 항목은 `해결됨`에 남깁니다. (작성일: 2026-11-04, 갱신일: 2026-11-07)

## 확인 방법 표기

| 표기 | 뜻 |
| --- | --- |
| **실행 확인** | 코드나 쿼리를 직접 실행해서 결과를 확인함 |
| **코드 추정** | 코드만 읽고 판단함. 실제 앱이나 실제 DB에서 재현하지 않았으므로 **추정**이며, 틀릴 수 있음 |

`해결됨` 항목을 제외한 모든 이슈는 수정되지 않은 상태입니다.

## 해결됨

### R-1. 날짜 문자열이 UTC 기준으로 계산되어 하루 밀림

- **확인 방법:** 실행 확인 (`src/utils/__tests__/date-test.ts`)
- **영향:** 서울 시간대에서 "이번 달"이 10-31 ~ 11-29로, "이번 주"가 일~토로 계산됨. 기본 날짜 `today`도 오전 9시 전에는 전날이었음
- **수정:** `toDateString`을 로컬 날짜 기준으로 변경. 특성화 테스트 커밋 `f33a02e` → 수정 커밋 `ea8935c`의 diff에서 전후 차이를 볼 수 있음
- **남은 문제:** 이미 저장된 기록은 D-1 참고. 앱을 켜 둔 채 날짜가 바뀌는 문제는 S-1 참고

### R-2. 날짜 필터 모달의 빈 칸 두 개

- **확인 방법:** 실행 확인 (사용자가 시뮬레이터에서 확인)
- **영향:** 기간 모드에 값이 들어가지 않는 칸 두 개가 표시되었음. 라벨은 커밋 `9746439`에서 지워졌고, 의도 여부는 확인하지 못했음
- **수정:** 값을 복원하지 않고 빈 칸 UI와 전용 스타일을 제거 (사용자 결정)

### R-3. 로그인 직후 pull 두 개가 겹쳐 동기화가 실패함

- **확인 방법:** 실행 확인 (실제 로그, 가짜 DB 재현 테스트 `src/sync/__tests__/cloud-sync-test.ts`, 시뮬레이터)
- **영향:** 세션과 커플 정보가 각각 pull을 시작해 같은 SQLite 연결에서 트랜잭션이 겹쳤습니다. `cannot start a transaction within a transaction`, `cannot rollback - no transaction is active` 오류가 나며 그 회차의 동기화가 실패했습니다.
- **수정:** pull과 push를 하나의 대기열로 순서대로 실행 (PR #4, `docs/decisions/0004-cloud-sync-and-edit-conflicts.md`)
- **남은 문제:** 로컬 저장·삭제는 대기열 밖입니다 (Y-6)

### R-4. 두 기기가 같은 기록을 고치면 먼저 저장한 내용이 사라짐

- **확인 방법:** 실행 확인 (두 시뮬레이터로 재현 후 수정 확인)
- **영향:** A가 일기를, B가 새로고침 없이 해시태그를 저장하면 B의 옛 일기가 함께 올라가 A의 일기가 경고 없이 사라졌습니다.
- **수정:** 서버 `version`과 조건부 UPDATE, 마지막 동기화 값 기준의 3-way 비교. 다른 칸은 자동으로 합치고 같은 칸은 선택 창 (PR #4)
- **남은 문제:** 사진은 비교하지 않습니다 (Y-7)

### R-5. 같은 해시태그를 두 번 입력하면 React key 경고가 남

- **확인 방법:** 실행 확인 (시뮬레이터 경고, `src/utils/__tests__/hashtag-test.ts`)
- **영향:** `#야경 #야경`이 그대로 저장되고 화면에서 같은 `key`로 쓰였습니다.
- **수정:** 입력할 때와 저장된 기록을 읽을 때 모두 중복 제거. 저장 값은 다시 저장할 때 정리됨 (PR #5)

### R-6. 세션 토큰을 암호화되지 않는 저장소에 보관함 (기존 P-1)

- **확인 방법:** 실행 확인 (`src/lib/__tests__/encrypted-session-storage-test.ts`, 재빌드한 시뮬레이터)
- **영향:** 리프레시 토큰이 들어 있는 세션이 AsyncStorage에 평문으로 저장되었습니다.
- **수정:** SecureStore에는 키만 두고 세션은 AES-GCM으로 암호화. 기존 평문 세션은 자동 이전 (PR #7, `docs/decisions/0005-session-encryption-and-safe-logs.md`)

### R-7. 오류 로그에 장소 정보와 외부 응답 원문이 남을 수 있음

- **확인 방법:** 실행 확인 (`src/utils/__tests__/error-log-test.ts`, `__tests__/api/naver-place-search-test.ts`)
- **영향:** 프록시가 장소 이름·주소와 네이버 응답 원문을 서버 로그에 남겼고, 앱은 오류 객체를 통째로 기록했습니다.
- **수정:** 앱은 `name`, `code`, `status`만, 프록시는 상태 코드와 오류 코드만 기록 (PR #6)

### R-8. 루트 README의 MVP 범위가 구현 상태와 다름 (기존 M-1)

- **확인 방법:** 코드와 문서 대조
- **수정:** README, 로드맵, 구조, 데이터 모델, 보안 문서를 현재 구현 기준으로 갱신

## 데이터

### D-1. R-1 수정 전에 저장된 기록의 날짜가 하루 이를 수 있음

- **확인 방법:**
  - 데이터 경로: 코드 추정
  - 아래 쿼리 동작: 실행 확인 (샘플 데이터로만 실행)
  - 실제 사용자 기록의 영향 여부: **미확인**. 기기의 DB와 Supabase 데이터를 조회하지 않음
- **영향:** 수정 전 코드에서는 추가 화면을 열 때 날짜 기본값이 `today`였습니다(`openAddPlaceModal`). 사용자가 날짜를 바꾸지 않고 저장했다면 전날 날짜로 저장되었을 수 있습니다.
  - 해당 코드는 첫 커밋(2026-06-26)부터 존재합니다.
  - 기준은 저장 시각이 아니라 **앱을 실행한 시각**입니다. `today`는 앱 시작 시 한 번만 계산되므로, 오전 8시에 켠 앱을 밤까지 유지했다면 밤에 저장해도 전날로 저장될 수 있습니다.
  - `date`에서 파생되는 `year`, `month`, `week_of_year`, `year_month`, `entry_<날짜>` ID도 함께 영향을 받습니다. 매월 1일 아침 기록은 이전 달로 분류될 수 있습니다.
  - 이 값들은 Supabase로도 업로드됩니다.
- **수정 방향:** 자동 변환하지 않습니다. 정상적으로 전날을 골라 저장한 기록과 구분할 수 없기 때문입니다. 후보를 뽑아 사용자가 직접 확인하고 앱의 수정 화면에서 고치는 방식이 안전합니다.

후보 조회 쿼리 (읽기 전용, 로컬 SQLite):

```sql
SELECT p.id, p.place_name, e.date,
       datetime(p.created_at, '+9 hours') AS created_kst,
       CAST(julianday(date(p.created_at, '+9 hours')) - julianday(e.date) AS INTEGER) AS gap_days
FROM date_places p
JOIN date_entries e ON e.id = p.date_entry_id
WHERE date(p.created_at, '+9 hours') > e.date
ORDER BY gap_days;
```

`gap_days`가 1 이상이면 후보일 뿐 버그 확정이 아닙니다. 지난 데이트를 나중에 기록한 경우나, 저장 후 날짜를 수정한 경우에도 나옵니다. 또한 앱을 실행한 시각은 어디에도 저장되지 않아 원인을 구분할 수 없습니다.

### D-2. 저장 기록을 최대 30개만 불러옴

- **확인 방법:** 코드 추정
- **영향:** `getSavedDatePlaces`의 기본 `limit`이 30입니다. 기록이 더 많으면 오래된 기록은 지도, 카드, 날짜 필터에서 빠지는 것으로 보입니다. `countDateCards`의 개수와도 달라집니다.
- **수정 방향:** 날짜 범위를 SQL 조건으로 내리거나 페이지네이션을 도입합니다.

### D-3. 로컬 `date_entries` ID가 커플 간에 충돌함

- **확인 방법:** 코드 추정
- **영향:** 서버 PK는 `(user_id, id)`이고 로컬 PK는 `id`뿐입니다. ID가 `entry_<날짜>`이므로 커플이 같은 날짜에 기록하면 pull에서 한 행이 덮어써져 `owner_user_id`가 바뀔 수 있습니다.
- **수정 방향:** 로컬 PK를 서버와 같은 복합키로 맞추거나, 사용자 ID를 포함한 ID로 마이그레이션합니다.

### D-4. SQLite 마이그레이션이 트랜잭션으로 묶여 있지 않음

- **확인 방법:** 코드 추정
- **영향:** `migrateDatabase`의 버전 단계 사이나 `ALTER TABLE` 두 줄 사이에서 실패하면, `user_version`이 올라가지 않은 채 일부만 적용됩니다. 재시도 때 `ALTER TABLE`이 중복 컬럼 오류로 실패할 수 있습니다.
- **수정 방향:** 버전별로 트랜잭션을 묶고 해당 단계의 `user_version`을 함께 올립니다. `PRAGMA journal_mode`는 트랜잭션 밖으로 분리해야 합니다.

## 동기화

### Y-1. 업로드 실패 시 자동 재시도가 없음

- **확인 방법:** 코드 추정
- **영향:** `pushDatePlace` 호출은 저장 시점 한 곳뿐이고, 실패는 `console.error`로만 남습니다. 오프라인에서 저장한 기록은 같은 기록을 다시 저장하기 전까지 서버에 올라가지 않을 수 있습니다. `cloud-sync.ts`의 "다음 push에서 재시도" 주석도 이 조건에서만 맞습니다. `pending_upload` 상태는 타입에만 있고 쓰이지 않습니다.
- **수정 방향:** 저장 시 `pending_upload`로 표시하고, 앱 시작이나 pull 시점에 미전송 기록을 다시 보내는 outbox(보낼 작업 대기열) 패턴을 도입합니다.

### Y-2. 업로드에 실패한 기록은 서버 변경을 받지 못함

- **확인 방법:** 코드 추정
- **현재 동작:** pull은 `sync_status`가 `synced`인 행만 덮어씁니다. 업로드되지 않은 로컬 수정이 옛 서버 값으로 사라지던 문제는 해결했습니다.
- **남은 영향:** 업로드에 실패했거나 충돌 선택 창을 답하지 않고 앱을 종료한 기록은 다시 저장하기 전까지 `local_only`로 남습니다. 그동안 다른 기기의 변경이 이 기기에 반영되지 않습니다.
- **수정 방향:** Y-1의 재시도 대기열을 도입하면 함께 해결됩니다.

### Y-3. 삭제한 기록이 되살아나거나 상대방 기기에 남을 수 있음

- **확인 방법:** 코드 추정
- **영향:**
  - `deleteRemoteDatePlace`는 Supabase가 반환하는 `error`를 확인하지 않습니다. Supabase 호출은 대개 예외를 던지지 않고 `error`를 돌려주므로 `try/catch`로 잡히지 않습니다.
  - 네트워크 실패로 서버 삭제가 안 되면 다음 pull에서 기록이 되살아날 수 있습니다.
  - pull은 서버에서 사라진 행을 로컬에서 지우지 않으므로, 상대방이 지운 기록이 내 기기에 남을 수 있습니다.
- **수정 방향:** `error`를 확인하고, 삭제 표시(soft delete, `deleted_at`)를 도입합니다.

### Y-4. 기록을 수정하면 사진이 중복될 수 있음

- **확인 방법:** 코드 추정
- **영향:** `updateDatePlace`는 로컬 사진 행을 지우고 새 ID로 다시 넣지만, 서버의 옛 `date_photos` 행과 Storage 파일은 지우지 않습니다. 다음 pull에서 옛 행이 새 사진으로 들어와 중복될 수 있습니다.
- **수정 방향:** 변경 없는 사진은 ID를 유지하고, 제거된 사진은 서버에서도 삭제합니다.

### Y-5. `backfillCoupleId`가 Supabase 오류를 확인하지 않음

- **확인 방법:** 코드 추정
- **영향:** 서버 업데이트가 실패해도 `error`를 확인하지 않아 로컬만 갱신될 수 있습니다. 이 경우 연결 전 기록이 상대방에게 보이지 않을 수 있습니다.
- **수정 방향:** 각 호출의 `error`를 확인하고, 실패 시 로컬을 갱신하지 않습니다.

### Y-6. 동기화와 로컬 저장·삭제의 트랜잭션이 겹칠 수 있음

- **확인 방법:** 코드 추정. pull끼리 겹치는 문제는 실제 로그와 테스트로 확인해 수정했고, 이 항목은 재현하지 않음
- **영향:** pull과 push는 하나의 대기열로 순서대로 실행되지만, `date-cards.ts`의 저장·수정·삭제는 대기열 밖에서 같은 SQLite 연결의 `withTransactionAsync`를 씁니다. pull 도중 저장하면 저장이 실패하거나, 실패한 쪽의 `ROLLBACK`이 다른 쪽의 작업을 취소할 수 있습니다.
- **수정 방향:** 모든 쓰기 트랜잭션이 하나의 대기열을 거치게 합니다. `withExclusiveTransactionAsync`도 후보이지만, 트랜잭션 안의 쿼리를 모두 `txn` 객체로 바꿔야 하고 다른 쓰기는 `database is locked`로 실패할 수 있어 검토가 필요합니다.

### Y-7. 사진은 기기 간 충돌을 감지하지 않음

- **확인 방법:** 코드 추정
- **해결된 부분:** 같은 계정의 두 기기가 같은 기록을 고치면 나중 저장이 전체를 덮어쓰던 문제는 두 시뮬레이터로 재현한 뒤 수정했습니다. `date_places.version`이 다르면 업로드가 거절되고, 앱이 서버 값을 다시 읽어 칸별로 비교합니다. 다른 칸은 자동으로 합치고, 같은 칸이면 선택 창을 보여 줍니다.
- **남은 영향:**
  - 대표 사진과 `date_photos`는 비교 대상이 아닙니다. 수정할 때마다 사진을 새 경로로 다시 올려서(Y-4), 비교하면 저장마다 충돌로 표시되기 때문입니다. 대표 사진은 나중 저장이 이깁니다.
  - `date_entries`의 업로드는 여전히 전체 upsert입니다. 지금은 `summary`를 앱에서 수정하지 않아 영향이 없습니다.
  - `version`을 모르는 이전 빌드는 서버 값을 덮어쓸 수 있습니다. 트리거가 버전은 올려 주므로 새 빌드는 이를 감지합니다.
  - 실시간 구독이 없어 다른 기기의 변경은 로그인 시점이나 당겨서 새로고침을 해야 보입니다.
- **수정 방향:** Y-4를 해결한 뒤 사진도 비교 대상에 넣습니다.

### Y-8. 로그인 직후 첫 pull이 `PGRST303`으로 한 번 실패할 수 있음

- **확인 방법:** 실행 확인 (2026-11-06 시뮬레이터와 Supabase API 로그). 원인은 추정
- **영향:** 로그인 성공 1초 뒤 `date_entries` 조회가 401 `JWT issued at future`로 실패했고, 같은 초의 `couples` 조회는 성공했습니다. Mac과 Supabase 서버의 시각은 1초 안으로 맞았습니다. 인증 서버와 DB API 서버 사이의 짧은 시각 차이로 추정합니다.
- **결과:** 실패한 pull은 다시 시도하지 않아, 기록이 있는 계정이 새 기기에서 로그인하면 새로고침 전까지 기록이 비어 보일 수 있습니다.
- **수정 방향:** `PGRST303`일 때만 잠시 뒤 횟수를 제한해 다시 시도합니다.

## 커플 공유

### C-1. 기록이 있으면 커플 연결 해제가 실패할 수 있음

- **확인 방법:** 코드 추정. `supabase/schema.sql` 기준이며 실제 운영 DB의 제약 조건은 미확인
- **영향:** `date_*` 테이블의 `couple_id`가 `ON DELETE` 규칙 없이 `couples(id)`를 참조합니다. 연결된 기록이 있으면 `couples` 삭제가 FK 오류로 실패할 수 있습니다. 호출부가 `void leaveCouple()`이라 오류가 처리되지 않고 사용자에게도 표시되지 않습니다.
- **수정 방향:** 제품 정책을 먼저 정합니다(해제 후 기록 공개 범위). 이후 `ON DELETE SET NULL` 등을 적용하고 호출부에 오류 처리를 추가합니다.

## 상태 / 구조

### S-1. `today`가 앱 시작 시 한 번만 계산됨

- **확인 방법:** 코드 추정
- **영향:** 모듈 최상단 상수라서, 앱을 켜 둔 채 자정이 지나면 날짜 기본값과 "이번 주/달" 필터가 어제 기준으로 남을 수 있습니다. R-1 수정으로 UTC 문제는 해결됐지만 이 문제는 남아 있습니다.
- **수정 방향:** 사용하는 시점에 계산하는 함수로 바꿉니다.

### S-2. `index.tsx`가 여전히 약 1,420줄

- **확인 방법:** 실행 확인 (줄 수 측정, 2026-11-07 기준 1,418줄)
- **영향:** 표시 컴포넌트와 조회용 상태는 분리했지만, 장소 편집기(상태와 JSX)와 설정·커플 연결이 아직 `HomeScreen`에 남아 있습니다.
- **수정 방향:** 보류한 분리 단위를 진행합니다: `SettingsModal` + `useCoupleLink`, 편집기 입력 섹션, `usePlaceEditor`.

### S-3. `createDateCard`와 `updateDatePlace`의 날짜 파생값 계산이 중복됨 (일부 해결)

- **확인 방법:** 코드 추정
- **해결된 부분:** 검색 텍스트는 `buildSearchText`로 묶었습니다 (PR #4).
- **영향:** 연도, 월, 주차 같은 날짜 파생값 계산은 아직 두 곳에 있어 한쪽만 고치면 값이 어긋날 수 있습니다. `getWeekOfYear`도 ISO 주차 계산이 아닙니다.
- **수정 방향:** 공통 함수로 묶어 테스트합니다.

### S-5. 쓰이지 않는 스타일이 남아 있음

- **확인 방법:** 실행 확인 (`index.tsx`에서 사용처 검색)
- **영향:** `quickRangeRow`, `quickRangeButton`, `quickRangeButtonText`는 정의만 있고 쓰이지 않습니다. 앱 동작에는 영향이 없습니다.
- **수정 방향:** 제거합니다.

## 보안

### P-2. 장소 검색 프록시에 호출 제한이 없음 (부분 해결)

- **확인 방법:** 인증 부분은 실행 확인, 호출 제한은 코드 추정
- **해결된 부분:** 로그인 세션 검증(401)과 오류 응답의 내부 정보 제거. 운영 배포에서 토큰 없는 호출과 가짜 토큰이 401을 받고, 앱의 로그인 세션으로는 검색되는 것을 확인했습니다. Vercel에 `SUPABASE_URL`, `SUPABASE_ANON_KEY`가 Production과 Preview 모두에 있어야 합니다.
- **남은 영향:** 이메일 OTP로 누구나 가입할 수 있으므로, 로그인한 사용자가 반복 호출해 네이버 API 쿼터를 소모하는 경우는 막지 못합니다.
- **수정 방향:** 사용자별 호출 제한을 추가합니다. 서버리스 인스턴스는 메모리를 공유하지 않으므로 외부 저장소나 Vercel 방화벽 규칙이 필요합니다. 사용 중인 플랜에서 가능한지는 미확인입니다.

### P-3. 네이버 장소 페이지를 비공식 스크래핑으로 조회함

- **확인 방법:** 코드 추정. 네이버 약관 위반 여부는 미확인
- **영향:** `resolveNaverPlaceUrl`은 네이버 모바일 검색 HTML을 정규식으로 파싱합니다. 페이지 구조가 바뀌면 동작하지 않으며(`null` 폴백은 있음), 약관 측면의 확인이 필요합니다.
- **수정 방향:** 약관을 확인하고, 공식 API나 지도 앱 딥링크 중심으로 재검토합니다.
