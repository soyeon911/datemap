# Known Issues

코드 분석 중 발견했지만 아직 고치지 않은 이슈를 기록합니다. (작성일: 2026-11-04)

## 확인 방법 표기

| 표기 | 뜻 |
| --- | --- |
| **실행 확인** | 코드나 쿼리를 직접 실행해서 결과를 확인함 |
| **코드 추정** | 코드만 읽고 판단함. 실제 앱이나 실제 DB에서 재현하지 않았으므로 **추정**이며, 틀릴 수 있음 |

`해결됨` 항목을 제외한 모든 이슈는 수정되지 않은 상태입니다.

## 해결됨

### R-1. 날짜 문자열이 UTC 기준으로 계산되어 하루 밀림

- **확인 방법:** 실행 확인 (`src/utils/__tests__/date-test.ts`)
- **영향:** 서울 시간대에서 "이번 달"이 10-31 ~ 11-29로, "이번 주"가 일~토로 계산됨. 기본 날짜 `today`도 오전 9시 전에는 전날이었음
- **수정:** `toDateString`을 로컬 날짜 기준으로 변경. 특성화 테스트 커밋 `f33a02e` → 수정 커밋 `ea8935c`의 diff에서 전후 차이를 볼 수 있음
- **남은 문제:** 이미 저장된 기록은 D-1 참고. 앱을 켜 둔 채 날짜가 바뀌는 문제는 S-1 참고

### R-2. 날짜 필터 모달의 빈 칸 두 개

- **확인 방법:** 실행 확인 (사용자가 시뮬레이터에서 확인)
- **영향:** 기간 모드에 값이 들어가지 않는 칸 두 개가 표시되었음. 라벨은 커밋 `9746439`에서 지워졌고, 의도 여부는 확인하지 못했음
- **수정:** 값을 복원하지 않고 빈 칸 UI와 전용 스타일을 제거 (사용자 결정)

## 데이터

### D-1. R-1 수정 전에 저장된 기록의 날짜가 하루 이를 수 있음

- **확인 방법:**
  - 데이터 경로: 코드 추정
  - 아래 쿼리 동작: 실행 확인 (샘플 데이터로만 실행)
  - 실제 사용자 기록의 영향 여부: **미확인**. 기기의 DB와 Supabase 데이터를 조회하지 않음
- **영향:** 수정 전 코드에서는 추가 화면을 열 때 날짜 기본값이 `today`였습니다(`openAddPlaceModal`). 사용자가 날짜를 바꾸지 않고 저장했다면 전날 날짜로 저장되었을 수 있습니다.
  - 해당 코드는 첫 커밋(2026-06-26)부터 존재합니다.
  - 기준은 저장 시각이 아니라 **앱을 실행한 시각**입니다. `today`는 앱 시작 시 한 번만 계산되므로, 오전 8시에 켠 앱을 밤까지 유지했다면 밤에 저장해도 전날로 저장될 수 있습니다.
  - `date`에서 파생되는 `year`, `month`, `week_of_year`, `year_month`, `entry_<날짜>` ID도 함께 영향을 받습니다. 매월 1일 아침 기록은 이전 달로 분류될 수 있습니다.
  - 이 값들은 Supabase로도 업로드됩니다.
- **수정 방향:** 자동 변환하지 않습니다. 정상적으로 전날을 골라 저장한 기록과 구분할 수 없기 때문입니다. 후보를 뽑아 사용자가 직접 확인하고 앱의 수정 화면에서 고치는 방식이 안전합니다.

후보 조회 쿼리 (읽기 전용, 로컬 SQLite):

```sql
SELECT p.id, p.place_name, e.date,
       datetime(p.created_at, '+9 hours') AS created_kst,
       CAST(julianday(date(p.created_at, '+9 hours')) - julianday(e.date) AS INTEGER) AS gap_days
FROM date_places p
JOIN date_entries e ON e.id = p.date_entry_id
WHERE date(p.created_at, '+9 hours') > e.date
ORDER BY gap_days;
```

`gap_days`가 1 이상이면 후보일 뿐 버그 확정이 아닙니다. 지난 데이트를 나중에 기록한 경우나, 저장 후 날짜를 수정한 경우에도 나옵니다. 또한 앱을 실행한 시각은 어디에도 저장되지 않아 원인을 구분할 수 없습니다.

### D-2. 저장 기록을 최대 30개만 불러옴

- **확인 방법:** 코드 추정
- **영향:** `getSavedDatePlaces`의 기본 `limit`이 30입니다. 기록이 더 많으면 오래된 기록은 지도, 카드, 날짜 필터에서 빠지는 것으로 보입니다. `countDateCards`의 개수와도 달라집니다.
- **수정 방향:** 날짜 범위를 SQL 조건으로 내리거나 페이지네이션을 도입합니다.

### D-3. 로컬 `date_entries` ID가 커플 간에 충돌함

- **확인 방법:** 코드 추정
- **영향:** 서버 PK는 `(user_id, id)`이고 로컬 PK는 `id`뿐입니다. ID가 `entry_<날짜>`이므로 커플이 같은 날짜에 기록하면 pull에서 한 행이 덮어써져 `owner_user_id`가 바뀔 수 있습니다.
- **수정 방향:** 로컬 PK를 서버와 같은 복합키로 맞추거나, 사용자 ID를 포함한 ID로 마이그레이션합니다.

### D-4. SQLite 마이그레이션이 트랜잭션으로 묶여 있지 않음

- **확인 방법:** 코드 추정
- **영향:** `migrateDatabase`의 버전 단계 사이나 `ALTER TABLE` 두 줄 사이에서 실패하면, `user_version`이 올라가지 않은 채 일부만 적용됩니다. 재시도 때 `ALTER TABLE`이 중복 컬럼 오류로 실패할 수 있습니다.
- **수정 방향:** 버전별로 트랜잭션을 묶고 해당 단계의 `user_version`을 함께 올립니다. `PRAGMA journal_mode`는 트랜잭션 밖으로 분리해야 합니다.

## 동기화

### Y-1. 업로드 실패 시 자동 재시도가 없음

- **확인 방법:** 코드 추정
- **영향:** `pushDatePlace` 호출은 저장 시점 한 곳뿐이고, 실패는 `console.error`로만 남습니다. 오프라인에서 저장한 기록은 같은 기록을 다시 저장하기 전까지 서버에 올라가지 않을 수 있습니다. `cloud-sync.ts`의 "다음 push에서 재시도" 주석도 이 조건에서만 맞습니다. `pending_upload` 상태는 타입에만 있고 쓰이지 않습니다.
- **수정 방향:** 저장 시 `pending_upload`로 표시하고, 앱 시작이나 pull 시점에 미전송 기록을 다시 보내는 outbox(보낼 작업 대기열) 패턴을 도입합니다.

### Y-2. pull이 업로드 전의 로컬 수정을 덮어쓸 수 있음

- **확인 방법:** 코드 추정
- **영향:** pull의 `ON CONFLICT DO UPDATE`는 `sync_status`나 `updated_at`을 비교하지 않습니다. 업로드되지 않은 로컬 수정이 서버의 옛 값으로 덮이고 `synced`로 표시될 수 있습니다.
- **수정 방향:** 미전송 행을 pull 대상에서 제외하거나, `updated_at`을 비교합니다. Y-1과 함께 다루는 편이 좋습니다.

### Y-3. 삭제한 기록이 되살아나거나 상대방 기기에 남을 수 있음

- **확인 방법:** 코드 추정
- **영향:**
  - `deleteRemoteDatePlace`는 Supabase가 반환하는 `error`를 확인하지 않습니다. Supabase 호출은 대개 예외를 던지지 않고 `error`를 돌려주므로 `try/catch`로 잡히지 않습니다.
  - 네트워크 실패로 서버 삭제가 안 되면 다음 pull에서 기록이 되살아날 수 있습니다.
  - pull은 서버에서 사라진 행을 로컬에서 지우지 않으므로, 상대방이 지운 기록이 내 기기에 남을 수 있습니다.
- **수정 방향:** `error`를 확인하고, 삭제 표시(soft delete, `deleted_at`)를 도입합니다.

### Y-4. 기록을 수정하면 사진이 중복될 수 있음

- **확인 방법:** 코드 추정
- **영향:** `updateDatePlace`는 로컬 사진 행을 지우고 새 ID로 다시 넣지만, 서버의 옛 `date_photos` 행과 Storage 파일은 지우지 않습니다. 다음 pull에서 옛 행이 새 사진으로 들어와 중복될 수 있습니다.
- **수정 방향:** 변경 없는 사진은 ID를 유지하고, 제거된 사진은 서버에서도 삭제합니다.

### Y-5. `backfillCoupleId`가 Supabase 오류를 확인하지 않음

- **확인 방법:** 코드 추정
- **영향:** 서버 업데이트가 실패해도 `error`를 확인하지 않아 로컬만 갱신될 수 있습니다. 이 경우 연결 전 기록이 상대방에게 보이지 않을 수 있습니다.
- **수정 방향:** 각 호출의 `error`를 확인하고, 실패 시 로컬을 갱신하지 않습니다.

## 커플 공유

### C-1. 기록이 있으면 커플 연결 해제가 실패할 수 있음

- **확인 방법:** 코드 추정. `supabase/schema.sql` 기준이며 실제 운영 DB의 제약 조건은 미확인
- **영향:** `date_*` 테이블의 `couple_id`가 `ON DELETE` 규칙 없이 `couples(id)`를 참조합니다. 연결된 기록이 있으면 `couples` 삭제가 FK 오류로 실패할 수 있습니다. 호출부가 `void leaveCouple()`이라 오류가 처리되지 않고 사용자에게도 표시되지 않습니다.
- **수정 방향:** 제품 정책을 먼저 정합니다(해제 후 기록 공개 범위). 이후 `ON DELETE SET NULL` 등을 적용하고 호출부에 오류 처리를 추가합니다.

## 상태 / 구조

### S-1. `today`가 앱 시작 시 한 번만 계산됨

- **확인 방법:** 코드 추정
- **영향:** 모듈 최상단 상수라서, 앱을 켜 둔 채 자정이 지나면 날짜 기본값과 "이번 주/달" 필터가 어제 기준으로 남을 수 있습니다. R-1 수정으로 UTC 문제는 해결됐지만 이 문제는 남아 있습니다.
- **수정 방향:** 사용하는 시점에 계산하는 함수로 바꿉니다.

### S-2. `index.tsx`가 여전히 약 2,500줄

- **확인 방법:** 실행 확인 (줄 수 측정)
- **영향:** 한 화면에 상태, DB 호출, 동기화, UI, 스타일이 모여 있어 변경 범위 파악과 테스트가 어렵습니다.
- **수정 방향:** 커스텀 훅과 화면 컴포넌트로 단계적으로 분리합니다.

### S-3. `createDateCard`와 `updateDatePlace`의 파생값 계산이 중복됨

- **확인 방법:** 코드 추정
- **영향:** 날짜 파생값과 검색 텍스트 계산이 두 곳에 있어 한쪽만 고치면 값이 어긋날 수 있습니다. `getWeekOfYear`도 ISO 주차 계산이 아닙니다.
- **수정 방향:** 공통 함수로 묶어 테스트합니다.

### S-5. 쓰이지 않는 스타일이 남아 있음

- **확인 방법:** 실행 확인 (`index.tsx`에서 사용처 검색)
- **영향:** `quickRangeRow`, `quickRangeButton`, `quickRangeButtonText`는 정의만 있고 쓰이지 않습니다. 앱 동작에는 영향이 없습니다.
- **수정 방향:** 제거합니다.

## 보안

### P-1. 세션 토큰을 암호화되지 않는 저장소에 보관함

- **확인 방법:** 코드 추정
- **영향:** `lib/supabase.ts`가 세션 저장소로 AsyncStorage를 씁니다. `expo-secure-store`는 의존성에 있지만, 실제 사용처와 도입하지 않은 이유는 확인하지 못했습니다.
- **수정 방향:** SecureStore 사용 또는 암호화 어댑터를 검토합니다. SecureStore의 값 크기 제한은 Expo v56 문서로 확인이 필요합니다.

### P-2. 장소 검색 프록시에 인증과 속도 제한이 없음

- **확인 방법:** 코드 추정. Vercel 쪽 별도 보호 설정은 미확인
- **영향:** `api/naver-place-search.js`는 CORS가 `*`이고 인증과 호출 제한이 없습니다. URL을 아는 누구나 호출해 네이버 API 쿼터를 소모할 수 있습니다. 오류 응답에 외부 API 응답 내용과 `VERCEL_ENV`도 포함됩니다. Client Secret을 서버에 둔 설계 자체는 유지할 가치가 있습니다.
- **수정 방향:** Supabase JWT 검증과 속도 제한을 추가하고, 클라이언트에는 오류 코드만 반환합니다.

### P-3. 네이버 장소 페이지를 비공식 스크래핑으로 조회함

- **확인 방법:** 코드 추정. 네이버 약관 위반 여부는 미확인
- **영향:** `resolveNaverPlaceUrl`은 네이버 모바일 검색 HTML을 정규식으로 파싱합니다. 페이지 구조가 바뀌면 동작하지 않으며(`null` 폴백은 있음), 약관 측면의 확인이 필요합니다.
- **수정 방향:** 약관을 확인하고, 공식 API나 지도 앱 딥링크 중심으로 재검토합니다.
