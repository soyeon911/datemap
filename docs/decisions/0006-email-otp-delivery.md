# Decision 0006: Email Codes Sent Through Custom SMTP

## 상태

Accepted

## 날짜

2026-11-06

## 배경

앱은 `signInWithOtp`로 이메일 6자리 코드를 보내고 `verifyOtp`로 확인합니다. 없는 이메일이면 계정이 자동으로 만들어집니다.

Supabase 기본 메일 서비스는 프로젝트 팀 멤버 주소로만 보내고, 시간당 2통으로 제한됩니다. 그래서 팀 멤버가 아닌 사람은 계정은 만들어져도 코드를 받지 못했습니다.

## 결정

Supabase Auth의 Custom SMTP를 Gmail(앱 비밀번호)로 설정합니다. 앱 코드는 바꾸지 않습니다.

새 계정이 받는 **Confirm sign up** 템플릿에도 `{{ .Token }}`을 넣습니다. 기존 템플릿에는 확인 링크만 있어, 새 계정은 코드 없는 메일을 받았습니다. 앱은 코드 입력 방식이므로 링크는 뺍니다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 가입 시 앱에서 Supabase 팀에 자동 추가 | 팀 멤버는 프로젝트 관리 권한을 가지며, 관리자 토큰을 앱에 넣어야 함. 저장소가 공개라 더 위험함 |
| 도메인을 인증한 메일 서비스 (예: Resend) | 앱 메일에는 더 적합하지만 본인 소유 도메인이 필요한 것으로 알고 있음 |
| 네이버 SMTP | 가능성은 있으나 절차를 확인하지 않음 |

## 설정 과정에서 확인한 것

Auth 로그에서 Gmail 응답을 보며 원인을 좁혔습니다.

| 응답 | 의미 | 조치 |
| --- | --- | --- |
| `535 Username and Password not accepted` | 인증 정보 거절 | 보내는 주소와 비밀번호 확인 |
| `534 Application-specific password required` | 2단계 인증 계정에 앱 비밀번호가 아닌 값을 넣은 경우에 주로 나옴 | 16자리 앱 비밀번호로 교체 |
| 메일은 왔지만 코드 없음 | Confirm sign up 템플릿에 `{{ .Token }}` 없음 | 템플릿 수정 |

## 한계

- 개인 Gmail이라 스팸 처리와 발송 한도 위험이 있다. 서비스 단계에서는 도메인을 인증한 메일 서비스로 옮긴다.
- 설정은 Supabase 대시보드에만 있고 저장소에는 없다. 앱 비밀번호는 저장소, `.env`, 로그 어디에도 두지 않는다.
- 팀 멤버가 아닌 다른 도메인 이메일(예: 네이버)로의 발송은 아직 시험하지 않았다.
