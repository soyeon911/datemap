# Decision 0004: Local-first Sync with Version-checked Uploads

## 상태

Accepted

## 날짜

2026-11-06

## 배경

기록은 기기의 SQLite에 먼저 저장하고, Supabase로 올리고 내려받습니다. 이 구조에서 두 가지 문제가 확인되었습니다.

- **기기 안의 경합:** 로그인 직후 세션과 커플 정보가 각각 pull을 시작했습니다. 같은 SQLite 연결에서 `withTransactionAsync`가 겹치면서, 실패한 쪽의 `ROLLBACK`이 다른 쪽의 트랜잭션을 취소했습니다. 실제 로그의 오류 두 줄을 가짜 DB 테스트로 같은 순서로 재현했습니다.
- **기기 간 덮어쓰기:** 업로드가 행 전체를 보냈습니다. 같은 계정의 두 시뮬레이터에서 A가 일기를, B가 새로고침 없이 해시태그를 저장하자 A의 일기가 경고 없이 사라졌습니다.

## 결정

1. **pull과 push를 하나의 대기열로 순서대로 실행한다.** 기다린 호출도 서버를 새로 읽는다.
2. **서버 `date_places`에 `version`을 두고, 업로드는 버전이 같을 때만 성공하는 조건부 UPDATE로 한다.** 버전은 서버 트리거가 올린다.
3. **버전이 다르면 서버 값을 읽어 마지막 동기화 값과 3-way 비교한다.** 서로 다른 칸은 자동으로 합치고, 같은 칸이면 사용자에게 선택 창을 보여 준다.
4. **pull은 아직 업로드하지 않은 로컬 수정을 덮어쓰지 않는다.**

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 진행 중인 pull 결과 공유 | 커플 연결 직후 연결 전 데이터를 받을 수 있음 |
| `withExclusiveTransactionAsync` | 트랜잭션 안의 쿼리를 모두 바꿔야 하고 다른 쓰기가 `database is locked`로 실패할 수 있음 |
| 나중 저장 우선 유지 | 먼저 저장한 수정이 경고 없이 사라짐 |
| `updated_at` 비교 | 기기 시계를 믿어야 함 |
| 비관적 잠금 | 수정 전에 서버 잠금을 잡아야 해서 오프라인 사용과 맞지 않음 |
| 앱이 버전을 올림 | `version`을 모르는 이전 빌드의 저장이 집계되지 않음 |
| 읽고 비교한 뒤 쓰기 | 비교와 쓰기 사이에 다른 기기가 끼어들 수 있음 |
| 같은 칸 충돌 시 서버 값 유지 | 사용자의 수정이 버려짐 (사용자 결정으로 선택 창 채택) |

## 범위와 한계

- 장소 이름, 주소, 좌표, 장소 ID는 함께 바뀌어야 의미가 맞으므로 하나의 묶음으로 비교한다.
- 사진과 대표 사진은 비교하지 않는다. 수정할 때마다 사진이 새 경로로 다시 올라가서(known-issues Y-4), 비교하면 저장마다 충돌로 표시된다.
- `couple_id`는 커플 연결 때 일괄 갱신되므로 트리거의 버전 증가 대상에서 뺀다.
- 로컬 저장·삭제 트랜잭션은 대기열 밖에 있다 (known-issues Y-6).
- 실시간 구독이 없어 다른 기기의 변경은 로그인 시점이나 당겨서 새로고침을 해야 보인다.

## 영향

- 서버: `supabase/migrations/0003_date_place_versions.sql`을 이 기능의 앱보다 먼저 적용해야 한다.
- 로컬: SQLite 버전 4에서 `date_places.server_version`, `synced_fields_json`을 추가했다.
- 코드: `app/src/sync/cloud-sync.ts`, `app/src/sync/date-place-merge.ts`, `app/src/components/home/ask-conflict-choice.ts`
